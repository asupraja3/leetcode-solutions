Walk me through how you built a RAG system end-to-end.

Your Answer
At Citadel, I prototyped a Conversational AI system using RAG — my pipeline had five stages: document ingestion → chunking → embedding → vector indexing → retrieval + generation.

For document ingestion, I loaded internal enterprise documents (PDFs, internal wikis) using document loaders in LangChain. I cleaned the text — removed headers, footers, irrelevant boilerplate — before processing.

What is hybrid search and when would you use it over pure vector search?
Very LikelyCiti JD Specific
▼
Your Answer

Hybrid search combines dense vector search (semantic similarity using embeddings) with sparse keyword search (like BM25) and merges results — typically using a technique like Reciprocal Rank Fusion (RRF).

When I'd use it: For the enterprise knowledge retrieval at Citadel, purely semantic search could miss exact document codes, product names, or compliance policy numbers. Hybrid search would catch both "what is the data retention policy" (semantic) AND "Policy-2024-DRP-003" (keyword match).

In a financial/banking context like Citi Controls Technology, this matters a lot — policy documents and controls frameworks have specific IDs and terminology that semantic search alone misses. I'd add BM25 keyword retrieval alongside vector search and merge with RRF before passing to the LLM.

💡 Say: "I've studied this pattern through NVIDIA's RAG Agent training and applied conceptually in the Agentic Medical Intelligence project where medical codes needed exact matching."
How do you handle hallucinations in a RAG system?
Very Likely
▼
Your Answer

Hallucinations in RAG can come from two places: retrieval failure (wrong chunks retrieved) or generation drift (LLM ignores the context). I address both:

  • Better retrieval: Check similarity scores — only pass chunks above a confidence threshold. If no good chunk exists, the system should say "I don't have information on that" rather than hallucinate.
  • Strict prompt constraints: In my Citadel system, I used system prompts like "Answer ONLY based on the context provided. If the answer isn't in the context, say so explicitly."
  • Re-ranking: Use a cross-encoder re-ranker to pick the most relevant retrieved chunk before injecting into the prompt.
  • Evaluation: Track faithfulness metrics — does the answer contain claims that can be traced back to the retrieved chunks?
💡 For Citi specifically, add: "In a banking compliance context, hallucinations are especially dangerous — I'd add an output validation layer that checks if key claims in the response are grounded in the retrieved chunks before serving to users."

What chunking strategy do you use and why does it matter?
Likely
▼
Your Answer

Chunking is how you break documents into pieces before embedding them. Poor chunking is one of the top reasons RAG systems fail.

In my Citadel system, I used recursive character text splitting with 512-token chunks and 50-token overlap. The overlap is important — it prevents cutting off a sentence mid-thought across chunk boundaries.

Other strategies I know: semantic chunking (chunk by topic/semantic coherence rather than fixed size — better for varied documents), document-structure chunking (split by headers/sections — great for PDFs with clear structure like policy documents at a bank), and sentence-level chunking for Q&A over dense technical content.

When would you choose fine-tuning over RAG?
Very LikelyCiti JD Specific
▼
Your Answer
For the Citadel enterprise knowledge system, I chose RAG over fine-tuning — and here's my reasoning framework for that decision.

Use RAG when: the knowledge base changes frequently (internal policies, market data), you need source citations, the data is sensitive and can't be baked into model weights, and you want lower cost (no training).

Use fine-tuning when: you need to teach the model a specific output format or writing style (e.g., always generate in JSON, always respond in compliance-approved language), domain vocabulary isn't in the base model's training, or you're doing tasks RAG can't help with (classification, sentiment that needs consistent calibration).

LoRA/QLoRA makes fine-tuning practical — instead of retraining all 7B+ parameters, LoRA adds small adapter matrices (~1% of parameters) to frozen layers. QLoRA adds 4-bit quantization on top, so you can fine-tune a 7B model on a single A100 GPU instead of needing a cluster.

Explain LoRA and QLoRA — what problem do they solve?
Very Likely
▼
Your Answer

Full fine-tuning of an LLM like LLaMA-2-7B requires updating all 7 billion parameters — that's extremely GPU-intensive and expensive. LoRA (Low-Rank Adaptation) solves this by adding small, trainable low-rank matrices to specific transformer layers while keeping the original weights frozen.

Think of it like adding sticky notes to a textbook instead of rewriting the whole book. The original knowledge stays intact; you just add domain-specific adjustments on top.

QLoRA goes further — it quantizes the frozen base model weights to 4-bit precision, dramatically reducing memory footprint. This lets you fine-tune a 7B parameter model on a single GPU that would otherwise need 4+ GPUs for standard LoRA.

In a banking context, you'd use QLoRA to fine-tune a base LLM on controls compliance language — so responses consistently use the right regulatory terminology and output format without RAG retrieval overhead.

The RAG system you deployed is returning irrelevant answers. Walk me through how you debug it.
Very LikelyIssue Handling
▼
Your Approach

I follow a structured debugging approach — isolate whether the problem is in retrieval or generation first.

  • Step 1 — Check what's being retrieved: Log the top-k chunks returned for the failing query. If the chunks are irrelevant, the retrieval layer is the problem. If they're relevant but the answer is wrong, generation is the issue.
  • Step 2 — If retrieval problem: Check similarity scores — are the scores low, suggesting no good match? Try the query in the vector store directly. Test different chunking sizes or embedding models. Check if the documents were properly ingested.
  • Step 3 — If generation problem: Check the prompt — is the injected context being ignored? Add stronger constraints: "Use ONLY the context below." Check if the LLM is hallucinating beyond the context or misinterpreting it.
  • Step 4 — Add hybrid search: If exact terminology is being missed, augment with BM25 keyword search — I'd implement this immediately as a fix.
  • Step 5 — Re-ranking: Add a cross-encoder re-ranker between retrieval and generation to improve chunk selection quality.
