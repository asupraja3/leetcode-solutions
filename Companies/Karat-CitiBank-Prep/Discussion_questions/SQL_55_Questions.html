MOST COMMONLY ASKED SQL CONCEPT

02WHERE vs HAVING — what's the difference?+
Answer

WHERE filters individual rows BEFORE grouping. HAVING filters groups AFTER aggregation.

-- WHERE: filter rows before GROUP BY
SELECT dept, AVG(salary) FROM employees
WHERE hire_date > '2020-01-01'
GROUP BY dept

-- HAVING: filter groups after aggregation
SELECT dept, AVG(salary) as avg_sal FROM employees
GROUP BY dept
HAVING AVG(salary) > 80000

You can use both: WHERE filters rows first, then GROUP BY aggregates, then HAVING filters groups.

03What is normalization? Explain 1NF, 2NF, 3NF+
Answer

1NF: Each column contains atomic values (no lists/arrays in a cell). Each row is unique.

2NF: 1NF + every non-key column depends on the entire primary key (not just part of a composite key).

3NF: 2NF + no transitive dependencies — non-key columns depend ONLY on the primary key, not on other non-key columns.

When to denormalize: Read-heavy analytics/reporting. Data warehouses often use star/snowflake schemas (denormalized) for query speed.

04What is the difference between DELETE, TRUNCATE, and DROP?+
Answer

DELETE: Removes specific rows (can use WHERE). Logged, can be rolled back. Triggers fire.

TRUNCATE: Removes ALL rows. Faster (minimal logging). Resets identity. Cannot use WHERE. Usually can't rollback.

DROP: Removes the entire table structure + data. Gone completely.

05What are indexes? When should you use them?+
Answer

Indexes are data structures (usually B-tree) that speed up data retrieval. Like a book index — instead of scanning every page, you look up where something is.

Use on: Columns in WHERE clauses, JOIN conditions, ORDER BY, GROUP BY. Primary keys are automatically indexed.

Don't over-index: Each index slows down INSERT/UPDATE/DELETE because the index must be maintained. Don't index low-cardinality columns (e.g., boolean).

06UNION vs UNION ALL+
Answer

UNION: Combines results and removes duplicates (requires sorting — slower). UNION ALL: Combines results and keeps duplicates (faster, no sort needed).

Use UNION ALL when you know there are no duplicates or when duplicates are acceptable. It's always faster.

07What is a subquery vs a CTE (Common Table Expression)?+
Answer

Subquery: Nested query inside another query. Can be in SELECT, FROM, or WHERE. Hard to read when deeply nested.

CTE (WITH clause): Named temporary result set. More readable, can be referenced multiple times, supports recursion.

-- CTE approach (preferred for readability)
WITH high_earners AS (
    SELECT dept_id, COUNT(*) as cnt
    FROM employees WHERE salary > 100000
    GROUP BY dept_id
)
SELECT d.name, h.cnt
FROM departments d JOIN high_earners h ON d.id = h.dept_id;

Performance: Usually identical. CTEs are not materialized in most databases (they're inlined). Use CTEs for readability.

08What are ACID properties?+
Answer

Atomicity: Transaction is all-or-nothing. Consistency: DB moves from one valid state to another. Isolation: Concurrent transactions don't interfere. Durability: Committed data survives crashes.

Critical in banking — a money transfer must debit AND credit atomically. If one fails, both must rollback.

09NULL handling — what are the gotchas?+
Answer

NULL is not a value — it's the absence of a value. Gotchas:

• NULL = NULL → NULL (not TRUE!). Use IS NULL / IS NOT NULL

• NULL in aggregates is ignored by SUM, AVG, COUNT(column) but NOT by COUNT(*)

• WHERE col != 'X' does NOT return rows where col is NULL

• Use COALESCE(col, default) to handle NULLs

10SQL order of execution+
Answer

Not the order you write it! Actual execution order:

1. FROM / JOINs     → identify tables
2. WHERE            → filter rows
3. GROUP BY         → create groups
4. HAVING           → filter groups
5. SELECT           → compute columns
6. DISTINCT         → remove duplicates
7. ORDER BY         → sort results
8. LIMIT / OFFSET   → paginate

This is why you can't use a column alias from SELECT in WHERE (WHERE runs before SELECT). But you CAN use it in ORDER BY.

11Find the second highest salary+
Schema: employees(id, name, salary, dept_id) 
-- Method 1: Subquery
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- Method 2: DENSE_RANK (handles ties)
SELECT salary FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) as rnk
    FROM employees
) ranked WHERE rnk = 2;

-- Method 3: OFFSET
SELECT DISTINCT salary FROM employees
ORDER BY salary DESC LIMIT 1 OFFSET 1;

12Find duplicate records+
Schema: emails(id, email) 
-- Find duplicate emails
SELECT email, COUNT(*) as cnt
FROM emails
GROUP BY email
HAVING COUNT(*) > 1;

To find and DELETE duplicates keeping the lowest id:

DELETE FROM emails
WHERE id NOT IN (
    SELECT MIN(id) FROM emails GROUP BY email
);
13Find employees who earn more than their manager+
Schema: employees(id, name, salary, manager_id) 
SELECT e.name AS employee
FROM employees e
JOIN employees m ON e.manager_id = m.id
WHERE e.salary > m.salary;

This is a self-join — joining the table to itself. The alias e represents employees, m represents their managers.

14Monthly active users and transaction totals for 2020+
Schema: transactions(id, user_id, amount, created_at) 
SELECT
    EXTRACT(MONTH FROM created_at) AS month,
    COUNT(DISTINCT user_id) AS active_users,
    COUNT(*) AS total_transactions,
    SUM(amount) AS total_amount
FROM transactions
WHERE created_at >= '2020-01-01' AND created_at < '2021-01-01'
GROUP BY EXTRACT(MONTH FROM created_at)
ORDER BY month;

Note: COUNT(DISTINCT user_id) for unique users, COUNT(*) for all transactions.

15Find customers who never placed an order+
Schema: customers(id, name), orders(id, customer_id, amount) 
-- Method 1: LEFT JOIN + NULL check
SELECT c.name
FROM customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE o.id IS NULL;

-- Method 2: NOT EXISTS (often faster)
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

-- Method 3: NOT IN (careful with NULLs!)
SELECT name FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders
                 WHERE customer_id IS NOT NULL);

17Pivot: count of orders per status per month+
Schema: orders(id, status, created_at) — status: 'pending','shipped','delivered' 
SELECT
    EXTRACT(MONTH FROM created_at) AS month,
    SUM(CASE WHEN status = 'pending' THEN 1 ELSE 0 END) AS pending,
    SUM(CASE WHEN status = 'shipped' THEN 1 ELSE 0 END) AS shipped,
    SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered
FROM orders
WHERE created_at >= '2024-01-01'
GROUP BY EXTRACT(MONTH FROM created_at)
ORDER BY month;

CASE WHEN inside aggregates = manual pivot. Essential pattern.

18Cumulative sum (running total)+
Schema: daily_sales(date, amount) 
SELECT
    date,
    amount,
    SUM(amount) OVER (ORDER BY date) AS running_total
FROM daily_sales;

Without ROWS BETWEEN, the default window frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW — perfect for cumulative sum.

20LAG and LEAD — accessing previous/next rows+
-- Day-over-day change in transactions
SELECT
    date,
    amount,
    LAG(amount) OVER (ORDER BY date) AS prev_day,
    amount - LAG(amount) OVER (ORDER BY date) AS daily_change
FROM daily_transactions;

LAG(col, n, default): Value from n rows BEFORE. LEAD(col, n, default): Value from n rows AFTER. Essential for comparing consecutive rows.

213-day rolling average+
SELECT
    date,
    amount,
    AVG(amount) OVER (
        ORDER BY date
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ) AS rolling_3day_avg
FROM daily_deposits;

ROWS BETWEEN: Defines the window frame. 2 PRECEDING AND CURRENT ROW = current row + 2 before = 3-day window.

⚠️ ROWS vs RANGE: ROWS counts physical rows. RANGE groups by value. For dates with gaps, ROWS might give wrong results — you may need to fill missing dates first.

22Top N per group (e.g., top 3 earners per department)+
WITH ranked AS (
    SELECT
        name, dept_id, salary,
        ROW_NUMBER() OVER (
            PARTITION BY dept_id
            ORDER BY salary DESC
        ) AS rn
    FROM employees
)
SELECT name, dept_id, salary
FROM ranked WHERE rn <= 3;

PARTITION BY: Restarts the ranking for each group (department). This pattern (rank + filter) is the #1 window function use case in interviews.

TOP KARAT/CITI SQL PATTERN

23Percent of total within group+
SELECT
    dept_id,
    name,
    salary,
    ROUND(salary * 100.0 / SUM(salary) OVER (PARTITION BY dept_id), 2)
        AS pct_of_dept_total
FROM employees;

SUM() OVER (PARTITION BY ...) without ORDER BY gives the total for the entire partition — perfect for percentage calculations.

24Detect consecutive events (e.g., 3+ consecutive days of login)+
WITH numbered AS (
    SELECT
        user_id, login_date,
        login_date - INTERVAL '1 day' * ROW_NUMBER()
            OVER (PARTITION BY user_id ORDER BY login_date) AS grp
    FROM logins
)
SELECT user_id, COUNT(*) AS streak, MIN(login_date), MAX(login_date)
FROM numbered
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

Gaps and Islands technique: Subtracting row_number from date creates the same value for consecutive dates. Brilliant pattern for detecting streaks.

25FIRST_VALUE / LAST_VALUE+
-- Each employee vs highest earner in their department
SELECT
    name, salary,
    FIRST_VALUE(name) OVER (
        PARTITION BY dept_id ORDER BY salary DESC
    ) AS top_earner,
    FIRST_VALUE(salary) OVER (
        PARTITION BY dept_id ORDER BY salary DESC
    ) AS top_salary
FROM employees;

⚠️ LAST_VALUE gotcha: default frame is up to current row, not end of partition. Use ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING for true last value.

OPTIMIZATION

4. Query Optimization & Performance

26How do you optimize a slow SQL query?+
Systematic Approach

1. EXPLAIN ANALYZE — read the query plan. Look for sequential scans, high row estimates, sorts.

2. Add indexes on WHERE, JOIN, ORDER BY columns.

3. Avoid SELECT * — only select needed columns.

4. Check JOINs — are you joining on indexed columns? Correct join type?

5. Reduce data early — filter in WHERE before JOINs when possible.

6. Avoid functions on indexed columns in WHERE (e.g., WHERE YEAR(date) = 2024 can't use index — use range instead).

7. Consider materialized views for expensive aggregations run repeatedly.

27Why is SELECT * bad?+
Answer

1. Fetches unnecessary data — more I/O, network transfer. 2. Prevents covering index optimization. 3. Breaks if table schema changes (new column appears). 4. Makes query intent unclear. Always explicitly list needed columns.

28Index anti-patterns — when indexes DON'T help+
Answer

• WHERE UPPER(name) = 'ALICE' — function on column prevents index use. Fix: functional index or store normalized.

• WHERE col LIKE '%abc' — leading wildcard = full scan. LIKE 'abc%' CAN use index.

• WHERE col != 'X' — negation often skips index (too many rows match).

• Low-cardinality columns (boolean, status with 3 values) — index doesn't help much.

• OR conditions across different columns — may not use indexes effectively.

29EXISTS vs IN — which is faster?+
Answer

EXISTS stops at the first match (short-circuits). IN may evaluate the entire subquery list.

Rule of thumb: EXISTS is faster when the subquery returns many rows. IN is fine for small lists. Modern optimizers often make them equivalent, but EXISTS handles NULLs better.

-- Prefer EXISTS for large subqueries
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
30What is a query execution plan? How do you read it?+
Answer

Run EXPLAIN (or EXPLAIN ANALYZE for actual timing). Key things to look for:

• Seq Scan (full table scan) — missing index?

• Nested Loop on large tables — consider hash join

• Sort — can an index eliminate sorting?

• Rows estimate vs actual — if very different, statistics are stale (ANALYZE table)

• Cost — higher startup cost = more setup. Higher total cost = more work overall.

31Calculate daily balance from transactions+
Schema: transactions(id, account_id, amount, type, date) — type: 'credit'/'debit' 
SELECT
    account_id,
    date,
    SUM(CASE WHEN type = 'credit' THEN amount
             WHEN type = 'debit' THEN -amount END)
        OVER (PARTITION BY account_id ORDER BY date) AS running_balance
FROM transactions
ORDER BY account_id, date;

Window function running sum — core banking calculation.

32Detect accounts with >40% daily balance drop+
WITH daily_bal AS (
    SELECT account_id, date,
        SUM(amount) AS balance
    FROM transactions GROUP BY account_id, date
),
with_prev AS (
    SELECT *,
        LAG(balance) OVER (PARTITION BY account_id ORDER BY date) AS prev_balance
    FROM daily_bal
)
SELECT * FROM with_prev
WHERE prev_balance > 0
  AND (balance - prev_balance) / prev_balance < -0.4;

LAG for previous day comparison. Relevant for fraud detection and anomaly monitoring at Citi.

33Year-over-year growth by product+
WITH yearly AS (
    SELECT
        product_id,
        EXTRACT(YEAR FROM date) AS yr,
        SUM(revenue) AS total
    FROM sales GROUP BY product_id, EXTRACT(YEAR FROM date)
)
SELECT
    curr.product_id, curr.yr,
    curr.total AS current_year,
    prev.total AS previous_year,
    ROUND((curr.total - prev.total) * 100.0 / NULLIF(prev.total, 0), 2)
        AS yoy_growth_pct
FROM yearly curr
LEFT JOIN yearly prev
    ON curr.product_id = prev.product_id
    AND curr.yr = prev.yr + 1;

Self-join on year offset. NULLIF prevents division by zero for new products.

34Find users active for 5+ consecutive days in January+
WITH jan_logins AS (
    SELECT DISTINCT user_id, DATE(login_time) AS login_date
    FROM logins
    WHERE login_time >= '2024-01-01' AND login_time < '2024-02-01'
),
grouped AS (
    SELECT user_id, login_date,
        login_date - (ROW_NUMBER() OVER (
            PARTITION BY user_id ORDER BY login_date
        ))::int AS grp
    FROM jan_logins
)
SELECT user_id, COUNT(*) AS streak_days
FROM grouped
GROUP BY user_id, grp
HAVING COUNT(*) >= 5;

Gaps and Islands technique again — Citi uses this for identifying consistent customer engagement patterns.

35Email click-through rate (CTR) by day+
Schema: emails(id, user_id, send_date, action) — action: 'sent','opened','clicked' 
WITH opened AS (
    SELECT send_date, COUNT(*) AS open_cnt
    FROM emails WHERE action = 'opened'
    GROUP BY send_date
),
clicked AS (
    SELECT send_date, COUNT(*) AS click_cnt
    FROM emails WHERE action = 'clicked'
    GROUP BY send_date
)
SELECT
    o.send_date,
    ROUND(c.click_cnt * 100.0 / NULLIF(o.open_cnt, 0), 2) AS ctr_pct
FROM opened o
LEFT JOIN clicked c ON o.send_date = c.send_date
ORDER BY o.send_date;

This is a reported Citigroup SQL interview question — calculating rates from event data.

38Identify dormant accounts (no transaction in 90 days)+
SELECT a.id, a.name, MAX(t.date) AS last_txn
FROM accounts a
LEFT JOIN transactions t ON a.id = t.account_id
GROUP BY a.id, a.name
HAVING MAX(t.date) < CURRENT_DATE - INTERVAL '90 days'
    OR MAX(t.date) IS NULL;

LEFT JOIN + NULL check catches accounts with zero transactions. HAVING filters on aggregated date.

39Monthly retention rate+
WITH monthly AS (
    SELECT DISTINCT user_id,
        DATE_TRUNC('month', txn_date) AS month
    FROM transactions
)
SELECT
    curr.month,
    COUNT(prev.user_id) AS retained,
    COUNT(curr.user_id) AS total,
    ROUND(COUNT(prev.user_id) * 100.0 / COUNT(curr.user_id), 2)
        AS retention_pct
FROM monthly curr
LEFT JOIN monthly prev
    ON curr.user_id = prev.user_id
    AND curr.month = prev.month + INTERVAL '1 month'
GROUP BY curr.month
ORDER BY curr.month;

Self-join on user + month offset. Retention = users who were active this month AND last month.

40SQL injection — how to prevent it+
Discussion Answer

Never interpolate user input into SQL strings. Use parameterized queries (prepared statements):

-- BAD: SQL injection risk
query = f"SELECT * FROM users WHERE id = {user_input}"

-- GOOD: Parameterized
cursor.execute("SELECT * FROM users WHERE id = %s", (user_input,))

ORMs (SQLAlchemy) handle this automatically. In banking, SQL injection could expose customer financial data — critical security concern.

    deposit_amount,

        PARTITION BY customer_id

FROM deposits

43What is a VIEW? When would you use one?+
Answer

A VIEW is a saved query — a virtual table that doesn't store data. Every time you query the view, the underlying SQL runs.

Use cases: Data abstraction (hide complex joins), security (restrict access to specific columns), consistency (everyone uses the same business logic).

Materialized View: Actually stores the result. Faster reads but needs refreshing. Good for expensive dashboards queried repeatedly.

44What are transactions and isolation levels?+
Answer

A transaction is a sequence of operations that are atomic. BEGIN → operations → COMMIT (or ROLLBACK).

Isolation levels (weakest to strongest):

1. Read Uncommitted — can see uncommitted changes (dirty reads)

2. Read Committed — only sees committed data (default in PostgreSQL)

3. Repeatable Read — same query returns same results within transaction

4. Serializable — transactions behave as if executed one at a time (slowest)

Banking typically uses Read Committed or higher to prevent financial data corruption.
